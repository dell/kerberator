# d3: Wrong realm on the Tenant

## Skill

`kerberator-diagnose-auth-failure` (DG-06)

## Why the fault is on the Tenant

The admission webhook refuses a Principal whose realm differs from its Tenant's, so
the original design, setting `spec.principal` to `svc-2001@WRONG.REALM`, can't be set up:

```
Error from server (Forbidden): admission webhook "update.principals.kerberator.dell.com" denied the request: spec.principal: Invalid value: "svc-2001@WRONG.REALM": principal tenant "WRONG.REALM" does not match the referenced Tenant "demo"'s spec.tenant "EXAMPLE.COM"
```

These tests don't touch or bypass the webhook. No equivalent check applied to the
Tenant, so this test creates the same mismatch from the other side.

## Preconditions

- Context is `kind-kerberator`, with the `make quickstart` environment.
- `./setup.sh d3` has run. It resets to healthy, sets the Tenant's `spec.realm` to
  `WRONG.REALM`, restarts the daemons to force a re-mint, and writes
  `~/.dg06-work/answer-key/d3.txt`.
- The Principal and `spec.daemon.krb5Conf` are not changed.

## Input

> Authentication is failing for Principal svc-2001 in namespace kerberator-demo. Can you figure out why?

This is the same prompt as d5, because the Principal really is Ready in this scenario.

## Expected behavior

**This scenario produces a mismatch, not a login failure.** The operator copies
`krb5.conf` from `spec.daemon.krb5Conf` and doesn't use `spec.realm` to build it, so
`kinit` for `svc-2001@EXAMPLE.COM` still succeeds against the KDC.

- Runs `collect.sh` and reports `nodes_failing=0/1`, `error_signature=none`, and a
  latest event of `KerberosMintSucceeded`.
- Says the evidence doesn't show a Kerberos ticket failure.
- Reports `realm_match=no`, quoting both realms: `EXAMPLE.COM` on the Principal and
  `WRONG.REALM` on the Tenant. It should also see that `krb5.conf` still says
  `default_realm = EXAMPLE.COM`.
- Says the mismatch needs correcting or checking with an owner, and doesn't present it
  as the cause of a failure it hasn't observed.
- Treats any failure the user sees as likely application-side, and says what it can't see.

**Fail if** it never mentions the realm mismatch, claims the mismatch is making `kinit`
fail, invents a cause from older events, or changes the Tenant.

**Known risk to this test:** the skill's classification may not reach the mismatch. Step 2
(`nodes_failing=0/N` and `error_signature=none`) comes before step 5 (`realm_match=no`).
An agent that follows the order strictly could stop at "Kerberator is getting tickets".
The report format does still ask for the realm under Evidence. If the agent omits the
mismatch, record it as a failure and flag the step order to the skill's author.
