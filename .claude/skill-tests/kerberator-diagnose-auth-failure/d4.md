# d4: Decoy keytab

## Skill

`kerberator-diagnose-auth-failure` (DG-06)

## Preconditions

- Context is `kind-kerberator`, with the `make quickstart` environment.
- `./setup.sh d4` has run. As in DG-03's T2, it creates `svc-2002@EXAMPLE.COM`, loads
  its keytab into `svc-2001-keytab`, and re-keys `svc-2001@EXAMPLE.COM` so the KVNOs
  differ. It then restarts the daemons and writes `~/.dg06-work/answer-key/d4.txt`.

## Input

> Principal svc-2001 in namespace kerberator-demo isn't Ready and can't authenticate to Kerberos. Can you figure out why?

## Expected behavior

- Runs `collect.sh` and classifies the failure as `keytab-no-matching-key`.
- Quotes the error: `Keytab contains no suitable keys for svc-2001@EXAMPLE.COM while getting initial credentials`.
- Says this is strong evidence that the keytab doesn't match this principal, most
  often because the wrong file was uploaded.
- Hands off to `kerberator-diagnose-keytab-kvno-mismatch` (DG-03) to compare the
  keytab's principal and enctypes.
- Treats `kvno_observed=2` with care. It describes the decoy's keytab, so a difference
  from the KDC's KVNO for `svc-2001` is not the finding.
- Doesn't have to name `svc-2002`. `collect.sh` never opens the keytab, so naming it
  needs a source the agent can cite. This differs from DG-03's T2.

**Fail if** the main finding is a KVNO mismatch or stale key, it recommends a rotation
without first establishing which keytab is correct, or it names `svc-2002` with no
evidence.

## Verification

1. `./capture.sh d4` reports `RESULT: matches prediction`.
2. `check.sh` passes S1-S4. This requires an agent run. See the README's note on
   hand-offs and S2.
3. A person grades the answer against the expected behavior above and S5.
4. `./setup.sh reset` reports healthy and `kubectl krb list -n kerberator-demo` shows 1/1.
